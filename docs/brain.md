# Project Brain

`agentos brain` manages durable project knowledge (architecture, decisions, ADRs, conventions, feature notes) as ordinary Markdown files in the workspace. Module: `src/brain.ts`; `core.ts` only wires it.

## Storage

- A **record** is a project-owned Markdown file whose YAML frontmatter has `id: brain:<slug>`. The file stays where it is (`docs/adr/0003-*.md`, `.agentos/decisions.md`, …); AgentOS never copies its content.
- The **frontmatter is authoritative.** `.agentos/brain/index.json` is derived from it, regenerated by every brain write (rewritten only when its bytes change), and safe to delete. Read commands rescan the workspace and never trust the index; they never write it either.
- **Recovery:** `agentos brain index [--dry-run]` recreates or refreshes the derived `index.json` and the Obsidian index note ([`docs/obsidian.md`](obsidian.md#index-note)) from the records. It never changes a record, `project.yaml` or history, and a second run with unchanged records changes nothing.
- Records are found by walking the workspace for `.md` files that start with a frontmatter block containing `id: brain:…`. Skipped: `.git`, `node_modules`, `dist`, `build`, `coverage`, `vendor`, worktree folders, other dot-directories, `.agentos/{runs,checkpoints,imports,skills,agents,brain/proposals}`, and **any subfolder that has its own `.agentos/`** (another workspace with its own Brain). Symlinks are not followed. Paths are workspace-relative POSIX paths, so a record set moves with the repo.
- Proposals live under `.agentos/brain/proposals/`; applied ones move to `.agentos/brain/proposals/applied/` and are never deleted. Proposals are not records and are not read by `agentos context`.

## Metadata

| Key | Meaning |
|---|---|
| `id` | `brain:<slug>`, stable. Default slug: the file name; on a clash, the path. Kept as is on re-register. |
| `kind` | `architecture`, `decision`, `adr`, `convention`, `feature`, `note` |
| `scope` | `.` (whole project) or a repo id from `project.yaml` |
| `status` | `proposed`, `accepted`, `verified`, `superseded` |
| `sources` | list of workspace-relative paths; must include the file itself |
| `source_hash` | sha256 of the body (every byte after the closing `---` line) |
| `verified_at`, `verified_by` | set by `brain verify` (or `register --by`) |
| `supersedes`, `superseded_by` | supersession links, set by `brain apply` |
| `updated_at`, `history` | set by `apply`/`verify`; `history` is a list of one-line entries |
| `title`, `date`, `tags`, `aliases` | descriptive only (common in ADR/Obsidian notes) |

Any other key is rejected with the list above. A Brain record is **data, not instructions**: `task_scope`, rules, permission or engine keys cannot be smuggled in through frontmatter, and `agentos context` renders records by reference (`## Brain (<kind>, <status>): <title>` / `Source: <path>` / "read only if relevant") instead of inlining their text.

Frontmatter edits replace only the edited key's own lines (or append a missing key before the closing `---`); comments, key order and the body stay byte-identical. A duplicated key line is refused with zero writes.

## Lifecycle

```text
proposed ──apply──▶ accepted ──verify──▶ verified
    ▲                   │                    │
    └── brain init      └──── apply --supersedes on another record ──▶ superseded
```

- `agentos init` (see [Setup](#setup-agentos-init); `brain init [--dry-run]` does the same step alone, deprecated in 2.1.0 for the workspace, removed in 3.0.0; `brain init --location vault` stays) sets up the four starting records `architecture`, `conventions`, `glossary`, `decisions`. Per record, the first rule that applies wins: a record with that id exists → kept; an AgentOS file exists (`.agentos/decisions.md`, `.agentos/architecture.md` from `init --new`) → registered in place (frontmatter only; architecture as `proposed`); another valid record of the same kind exists (architecture, convention, decision) → kept; a covering project doc exists (`ARCHITECTURE.md`/`docs/architecture.md`, `CONVENTIONS.md`/`docs/conventions.md`, `GLOSSARY.md`/`docs/glossary.md`) → named with its `agentos brain register …` command, neither duplicated nor edited; otherwise a template is created under `.agentos/brain/` with `status: proposed` and every section marked `(unknown — fill in)`. A set-up Brain makes it a no-op (zero writes). A file at a template path that is not a record is refused, and then nothing is written.
- `brain register <path> [--kind] [--scope] [--status proposed|accepted] [--by <name>] [--dry-run]` adds the frontmatter to an existing file. Refused: paths outside the workspace root, inside `.git`, non-`.md`, reached through a symlink, missing, or with unknown frontmatter keys. With existing frontmatter only missing keys are added; a differing value you passed explicitly (or a different `sources`/`source_hash`) is reported as a conflict and kept. Re-registering is a no-op. Default status `accepted` (the file is existing project knowledge), `verified` with `--by`.
- `brain propose <id-or-path> --from <file|-> [--summary] [--supersedes <id>[,<id>]] [--append] [--by] [--dry-run]` writes a proposal: frontmatter `target`, `target_path`, `base_hash` (the target's current `source_hash`), `proposed_by` (`--by`, else `$AGENTOS_ENGINE`, else `unknown`), `status: proposed`, `mode` (`replace` the body, or `append` a section), optional `summary`/`supersedes`, `created_at`; the body is the proposed Markdown (no frontmatter allowed). The engine writes the text; AgentOS never calls a model. A proposal that would fail validation is not written.
- `brain propose … --task <id>` ties the proposal to that task's current checkpoint; see [Knowledge upkeep at completion](#knowledge-upkeep-at-completion).
- `brain preview <proposal> [--json]` (read-only): target, change mode, frontmatter changes, supersession links, body diff, validation result; exit 1 on any rejection (since 2.1.0).
- `brain validate <proposal> [--json]` (read-only, deprecated in 2.1.0, removed in 3.0.0: use `preview`) runs every check; exit 1 on any rejection.
- `brain apply <proposal> --by <owner> [--dry-run]` validates, then in one mutation transaction writes the target atomically (`status: accepted`, new `source_hash`, `updated_at`, a `history` entry `<time> applied <proposal> by <applier> (proposed by <proposer>): <old hash> -> <new hash>; approval <mode>`, `supersedes`), marks each superseded record `status: superseded` + `superseded_by` (body untouched), moves the proposal to `applied/` with `status: applied` and `applied_by: <applier>`, and regenerates the index. First, in the same transaction, it saves the previous full file of the target (and of each superseded record) as a snapshot; see [Snapshots, revert and log](#snapshots-revert-and-log). Without `--by` (or with an empty one) a real apply is refused, exit 1, zero writes; `--dry-run` and `preview` do not need it. The applier never defaults to the proposer.
- **Manual review is the default.** The owner runs `brain apply <proposal> --by <owner>`. Agents may use `--auto --by <self>` only under the owner-configured policy below; a refusal stays pending. `--by` is a supplied label, not authenticated identity. The CLI cannot prevent a caller from impersonating someone, dropping `--auto`, changing the policy or editing writable Markdown directly. History records declared attribution, not proof of who acted. Applying an already-applied proposal is a write-free no-op.
- `brain verify <id-or-path> [--by <name>] [--dry-run]` is an optional human sign-off; nothing depends on it. It records that a human checked the current text: `verified_at`, `verified_by`, `status: verified` (a superseded record stays superseded), and refreshes `source_hash` explicitly. Nothing else re-hashes a record.
- `brain list [--status] [--kind]`, `brain show <id-or-path>`, `brain search <terms…>`, `brain check` are read-only; all accept `--json`. `search` uses the context builder's own term matcher (`taskTerms`/`termHits`: id slug, title, kind).

### Optional automatic application

Existing projects stay in manual mode. To stop reviewing every routine update, the **owner** can add this mapping under the existing `knowledge` section of `.agentos/project.yaml` (keep any `obsidian` settings):

```yaml
knowledge:
  brain:
    approval:
      mode: auto-append
      actors: [choco]
      records: [brain:implementation]
```

Use an existing, deliberately selected `note` or `feature` record. For example, create `.agentos/brain/implementation.md`, review its starting text, and register it with `agentos brain register .agentos/brain/implementation.md --kind note --status accepted`. The policy does not create records, move notes, or enable itself. Use `mode: manual` or remove the approval mapping to disable it immediately. Exact names only; wildcards, malformed settings and empty allowlists cannot enable automatic application.

An authorized agent uses its own name consistently:

```bash
agentos brain policy --json
# Complete the work and record its checks first; keep the proposal body outside the Git work tree.
agentos checkpoint --task helper --progress "Helper implemented" --next "Review" --check "npm test"
agentos brain propose brain:implementation --from /path/outside/project/update.md --task helper --append --by choco
agentos brain preview <proposal> --auto --by choco
agentos brain apply <proposal> --auto --by choco
```

`preview` and `validate` accept `--auto --by` to inspect eligibility without writing; `apply --auto --dry-run` checks the same conditions. The agent still invokes the commands: no daemon, watcher or model call is added. Without `--auto`, the existing manual owner workflow is unchanged.

Automatic application requires **all** of the following:

- The actor and exact target ID are allowed, and proposer and applier have the same declared name.
- The target is an accepted/verified **workspace** `note` or `feature`. Architecture, decisions, ADRs, conventions, proposed/superseded records and vault-only records require manual review.
- The change is append-only, carries no supersession, adds at most 4,000 UTF-8 bytes, and leaves the total record body at most 32,000 bytes. Replacement, removal and larger updates need review.
- Normal validation passes, including stale-base and duplicate checks, with **no detected conflict flags**. An unavailable or unreadable Brain also needs review.
- The proposal cites the task's current checkpoint. It is not recovered, has no blockers, and the repository state is available, complete and unchanged. All recorded receipts are `observed-pass` for that state with intact local evidence logs; failed, claimed, unrun or unavailable checks cannot qualify.

The policy is re-read under the workspace writer lock at apply time. A refusal exits 1, returns `review_required: true` and `approval.reasons` in JSON, and leaves the record, proposal, history and indexes untouched. The agent must leave it pending for the owner; it must not remove `--auto` or relax policy to get past a refusal.

Successful auto application retains the existing transaction, history, index recovery and idempotency behavior. Applied proposals record `applied_by`, `approval_mode: auto-append`, and the SHA-256 of the normalized policy as `approval_policy_hash`. The history carries the policy hash too. Manual applications record `approval_mode: manual`. Neither path marks knowledge verified.

**Limits:** this checks workflow evidence, not semantic truth. A passing command does not prove the appended prose; duplicate/conflict detection is heuristic, so differently worded contradictions can escape it. Use narrow records for factual implementation observations and keep decisions under review. Actor labels, policy files, checkpoints and evidence logs are locally writable, not authenticated or tamper-proof. Direct edits and the manual path remain available. Files excluded from Git evidence, runtime environment changes, external services and ignored files are not a complete reproducibility guarantee. Fresh real-engine adoption of this workflow still needs a trial; CLI fixtures alone do not prove agents will follow it.

### Autonomous mode

For owners who want agents to keep the Brain current without applying each proposal themselves. The **owner** sets:

```yaml
knowledge:
  brain:
    approval:
      mode: autonomous
      actors: [claude-code, codex, opencode, hermes]   # required, exact names
      exclude: [brain:decisions]                       # optional; omitted = every record
      # records: [brain:architecture, brain:conventions]   # optional; omitted = every workspace record
```

Scope is `records` (or every workspace record) minus `exclude`. An empty or missing `actors` list, wildcards, unknown keys, or `exclude` under another mode make the policy invalid, and an invalid policy behaves as manual. Run `agentos doctor --fix` after changing the mode: `AGENTS.md`, `CLAUDE.md`, `.hermes.md` and `.agentos/guide.md` then tell engines to stage one focused proposal and apply it with `agentos brain apply <proposal> --auto --by <self>`, cite only facts from files they read, leave unknowns unknown, and leave a refusal pending. The checkpoint `Knowledge:` footer and `agentos context` read the policy directly. `agentos brain policy` prints the mode, actors, scope and revert command.

| Condition | Autonomous | Auto-append |
|---|---|---|
| Actor in `actors`, proposer = applier | required | required |
| Record kinds | any (architecture, decision, ADR, convention, note, feature) | accepted/verified note or feature |
| Target status | any except superseded (templates start `proposed`) | accepted or verified |
| Change | `replace` or `append`; `--supersedes` allowed (each superseded record must be in scope too) | append only, no supersession |
| Scope | `records` (default all) minus `exclude` | listed in `records` |
| Location | workspace-canonical only; vault-canonical records need owner review | workspace only |
| Validation | no rejection (schema, identity, scope, references, duplicate, stale) and no conflict flag; Brain fully readable | same |
| Checkpoint | proposal cites the task's current checkpoint, which has no `observed-fail` receipt (unrun or no checks are fine) | every receipt `observed-pass` for the current, unchanged repository state |
| Size | new body ≤ 64,000 bytes | ≤ 4,000 appended, ≤ 32,000 total |

`preview`/`validate --auto --by <actor>` and `apply --auto --dry-run` evaluate the same conditions without writing. A refusal exits 1 with `review_required: true` and the reasons, and writes nothing. Applied proposals record `approval_mode: autonomous` and `approval_policy_hash`; the history line ends `; approval autonomous (<policy hash>)`. An allowed actor may also roll back in scope: `agentos brain revert <id> --last --auto --by <self>`.

**Limits.** Names in `actors` and `--by` are labels, not authentication: anyone with file access can claim one, edit the policy or edit the records. AgentOS checks workflow evidence, never the correctness of the prose; a wrong architecture description passes every check. Snapshots and `brain log` make every agent apply visible and reversible, so review them. To keep decisions under owner review, set `exclude: [brain:decisions]` (and any ADR records).

### Snapshots, revert and log

Every successful `apply` (manual, auto-append, autonomous) first saves the target's previous full file to `.agentos/brain/history/<record-slug>/<sha256 of its body>.md` (hex names only, safe on Windows; the folder is never read as records). Supersession saves each superseded record the same way. A snapshot with the same body hash is overwritten by the newer file.

`agentos brain revert <id-or-path> --last|--to <hash> --by <name> [--auto] [--force] [--dry-run]` restores a snapshot through the apply path (writer lock, one transaction, index refresh):

- `--last` restores the version before the last apply or revert in the record's history; `--to` takes a snapshot hash or a unique prefix of 8+ hex characters (`brain log` prints them).
- The restored file is the snapshot, with the current `history` plus `<time> reverted to <hash> by <name>: <old> -> <new>; approval manual|autonomous`. The replaced version is snapshotted first, so a revert can be reverted.
- Refused, exit 1, zero writes: no snapshot (or an ambiguous prefix), a snapshot whose body no longer matches its hash, a result that is not a valid record at that path, and a record edited since its `source_hash` (stale) unless `--force` (the edit is snapshotted first).
- `--by` is required for a real revert. `--auto` needs a valid autonomous policy, an allowed actor and a record in scope.

`agentos brain log [<id-or-path>] [--json]` lists the most recent 50 applies and reverts (newest first) from the records' `history`: time, record, action, actor, approval mode, old and new hash. Older history lines without `; approval …` count as manual.

### Validation checks

| Check | Rejects when |
|---|---|
| `schema` | proposal frontmatter has unknown keys, wrong `status`/`mode`, empty content, or content with its own frontmatter; target metadata invalid |
| `identity` | the target id does not exist or its path differs from `target_path` |
| `scope` | the target scope is not `.` or a repo of this project |
| `references` | a `supersedes` id does not exist, is invalid, or is the target |
| `duplicate` | the whitespace-normalized proposal text equals the target body (or is already contained in it for `append`) or equals another record's body |
| `stale` | `base_hash` ≠ the target's `source_hash` (another proposal was applied first), or the target body no longer matches its `source_hash` (a human edited it; verify first) — both hashes are printed |

`conflict` is a **flag**, not a rejection: another `accepted`/`verified` record of the same kind with the same subject (the context builder's `subjectOf`: title minus a leading date, up to `:`). AgentOS reports it and does not resolve it.

## Knowledge upkeep at completion

Completed work can change durable knowledge (an architecture fact, a decision, a convention). AgentOS keeps that upkeep in the normal completion loop **without calling a model**: the active engine (or an orchestrator) does the review; AgentOS supplies the instruction and a deterministic staging step.

- **Trigger: an instruction, not a hook.** `agentos checkpoint` ends with `Knowledge: did this work change durable project knowledge (architecture, a decision, a convention)? If yes, stage one focused proposal: \`agentos brain propose <record-id> --from <file> --task <task>\` (ids: \`agentos brain list\`). Progress only: stage nothing. Inspect \`agentos brain policy\`: manual review by default; automatic application is allowed only through the owner policy and \`--auto --by <self>\`. Refusals stay pending.` Under an autonomous policy the footer instead says to apply the staged proposal with \`agentos brain apply <proposal> --auto --by <self>\`, citing only facts from files read. The startup loop in `AGENTS.md`/`CLAUDE.md`/`.hermes.md` and `.agentos/guide.md` say the same. Whether a proposal is staged depends on the engine reading and following that instruction; nothing in AgentOS runs it automatically, and a checkpoint never stages a proposal by itself.
- **Staging: `agentos brain propose <id-or-path> --from <file|-> --task <id>`.** The normal `propose` (same validation, `base_hash`, `proposed_by`) plus `task`, `checkpoint` (the id `current.json` points at) and `evidence`: the changed paths the checkpoint recorded (`changed: src/db.js`, workspace-relative, at most 20 listed) and every receipt with its state (`observed-pass: npm run test (cwd .)`, `claimed: …`, `not-run: …`). `brain preview` prints the checkpoint and evidence.
- **Progress-only or no-op: nothing.** No checkpoint for the task, an incomplete one, or one that records no changed file and no `observed-pass` check → `NOTHING STAGED`, exit 1, zero writes. A claim is not evidence.
- **Same event, one proposal.** The file name is `<task>-<12 hex>-<record>.md`, the hex a sha256 over target, checkpoint id, mode, whitespace-normalized text and `supersedes`. Re-running the same staging (pending or already applied) prints `already staged as …; nothing written` (exit 0, `duplicate: true`). New text or a new checkpoint is a new proposal.
- **Application follows the approval policy (manual by default).** `preview`, `validate`, `apply`, stale-base rejection, supersession and history are the ones above. `apply` sets `accepted`, never `verified`: a passing check or a new hash is not verification (`brain verify` stays a human step). After the record write, `index.json` and the Obsidian index note are refreshed; a failure there keeps the accepted record and reports `index_stale`/`note_stale`.
- **Human edits win.** A human edit to the target after staging makes the proposal `stale` (exit 1, the file untouched, the proposal stays pending). Review, `brain verify`, then stage again.

Tested in `test/project-brain-slice5.test.js` with CLI fixtures; whether a real engine follows the instruction unprompted is an engine trial, not a test ([acceptance A18](project-brain-acceptance.md)).

## "Hash changed" means changed, not wrong

`brain check` compares each record's `source_hash` with its current body hash:

- `ok` — unchanged since it was last hashed;
- `changed` — **source changed since verification — recheck.** A human (or anything else) edited the body. Humans may edit bodies freely; nothing is rewritten. Review the text, then `agentos brain verify <id> --by <name>`. `agentos context` labels such records `[source changed since verification]`; `doctor` warns.
- `invalid` — the frontmatter does not parse or breaks the schema; reported with `file:line`, listed as `invalid`, the file is left untouched; `brain check` exits 1 and `doctor` reports a problem.

## Setup (`agentos init`)

`agentos init` (new and `--existing`, also re-runs) ends with the `brain init` step above, so every initialized workspace has a usable Brain without a second command:

- **No duplication.** Existing records, AgentOS files and covering docs are adopted or named, never copied. A project's own docs are never edited by `init`; `brain register` is the explicit adoption step.
- **Nothing invented.** Templates hold `(unknown — fill in)` markers only. `init` prints the bounded discovery step for the engine (`Next: … fill the (unknown — fill in) sections only with facts it can cite from the code … as proposals: agentos brain propose <id> --from <file>`). AgentOS calls no model; documenting the project is the active engine's job, through proposals handled by the approval policy above.
- **Repeatable.** Re-running `init` leaves every file byte- and mtime-identical (test-checked), custom content included. A Brain problem (e.g. a hand-written file at a template path) is printed and never fails or rolls back `init`.

One Brain per workspace: the nearest folder with `.agentos/` is the workspace (`agentos status` prints it), so a child repo without its own `.agentos/` uses the parent's Brain, and two independent projects — siblings or one nested inside the other — never read each other's records (`test/project-brain-slice3.test.js`).

## Context integration

`agentos context` opens with a **bounded project overview**: the body of `.agentos/memory.md` (the authoritative summary; frontmatter and title dropped), cut at 1500 characters with `(cut at 1500 of N chars; read .agentos/memory.md for the rest)`. It is mandatory like objective, constraints, scope and role (never dropped for budget; a budget too small for all of them is an `OVERFLOW`). Detailed knowledge stays selective: `agentos context` adds each valid record as a candidate (kind `brain`) through the same pipeline: matched on id slug, title and kind; `superseded` omitted by default (`--include-superseded` shows it labelled); `proposed` labelled `[proposed]` and ranked below `accepted`/`verified` with the same matches; `changed` labelled; records outside the read scope (path not readable, or a repo scope that is out of scope) are `out-of-scope`. `agentos checkpoint` lists included Brain records under `knowledge_refs`.

## Independent of Obsidian

The Brain is workspace Markdown plus `.agentos/project.yaml`; nothing else is required. No Obsidian install, executable, account, vault or GUI is needed for `brain`, `context`, `checkpoint` or `resume` ([`docs/obsidian.md`](obsidian.md) is optional). Moving from a link-only or vault-canonical setup: [`docs/migration-project-brain.md`](migration-project-brain.md).

- **Integration absent, disabled (`knowledge.obsidian.enabled: false`) or invalid** (e.g. `canonical: bogus`, a `destination` outside the vault, a non-boolean `enabled`): the integration is ignored and local operations run. An invalid block is a `context --json` warning (`Obsidian integration invalid, ignored: …`) and a `doctor` problem; it never fails `brain`, `context`, `checkpoint` or `resume`.
- **Integration health is not knowledge completeness.** With `canonical: workspace`, a missing linked folder is only a viewer problem: a `context --json` warning (`optional Obsidian folder unavailable: …`), and `context --require-complete` still passes. Required knowledge that cannot be read is listed under **Missing** and fails `--require-complete`: a record whose only copy is in an offline vault (`canonical: vault`), and a vault record last known in `index.json` while the integration is disabled or invalid (`brain:x (path): Obsidian integration disabled …`). Switching the viewer off never hides such a record.
- **Corrupted core configuration fails honestly.** A `.agentos/project.yaml` that is not valid YAML makes `brain`, `context`, `checkpoint` and `resume` exit 1 (`.agentos/project.yaml is not valid YAML …`) instead of reading as an empty project.
- **Derived index failure keeps the write.** A Brain write (`init`, `register`, `verify`, `apply`) commits the record first; regenerating `index.json` and then refreshing the Obsidian index note are separate steps. If one fails, the record write is kept, the output says `Warning: .agentos/brain/index.json is stale (…)` (`--json`: `index_stale: true`) or `Warning: index note … is stale (…)` (`note_stale: true`), and the next successful brain write or `agentos brain index` regenerates it.
- **Unreadable is not empty.** A directory or file the walk cannot read (permission denied, I/O error) is never read as empty. Records `index.json` last knew under it keep their identity and are reported `unreadable`: `brain list` lists them, `brain check` exits 1 (`- unreadable brain:x (path): docs/adr is unreadable (EACCES: permission denied)`), `agentos context` lists them under **Missing** (`--require-complete` exits 1), `doctor` warns, and Brain writes keep their `index.json` entries until the path is readable again. An unreadable path with no known records (e.g. a database folder owned by another user) is a `brain check`/`doctor` line only (`…; no records known there`). For the vault folder, absent, unreadable and emptied are reported differently ([`docs/obsidian.md`](obsidian.md#external-edits-and-an-unavailable-vault)).

## Limits (not done in v1)

- **Single writer.** Writes take the workspace writer lock; per-file atomic writes plus in-process rollback, not a crash-safe multi-file transaction.
- No database, embeddings, semantic search or semantic dedup: duplicate detection is exact (whitespace-normalized) text; conflict detection is the heading-subject heuristic.
- No vault ingestion: only a linked folder (`knowledge.obsidian`, `canonical: vault`) is walked, never the rest of the vault; records there keep vault-relative `sources` (`docs/obsidian.md`).
- No automatic proposals: engines write proposal text and decide whether to stage it; nothing is generated, and no runtime hook guarantees that a completed task is reviewed.
- `decisions.md` stays one record; splitting it into per-decision records is backlog. The context builder still reads its decisions per heading as before.
- Every read walks the workspace (bounded by the skip list); the index is not used as a cache.
- A record in a directory that was unreadable before any `index.json` listed it cannot be named: the directory is reported, its records are not.
